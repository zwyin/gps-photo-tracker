# 移动端支持可行性调研（iOS/Android）

> 2026-09-11 · 任务 #8 brainstorming 产出 · 结论先行：**不建议现阶段投入原生移动端**，推荐"先补桌面移动场景短板"的轻路线。

## 现状盘点

- GUI：PySide6 桌面应用（4363 行 gui/ 代码），macOS/Windows/Linux 三平台打包（dist/ 已有 .app 与 onefile）
- 核心能力：GPX/FIT/TCX 解析、GPS 匹配、EXIF 写入、CLI 完整（v0.26.0）
- 用户场景假设：旅行中拍照（手机）+ 运动手表记录轨迹 → 回到电脑批量写入。**真正的移动场景痛点是"当天在手机上就想看哪些照片还没打标"**，而非手机上做 EXIF 写入

## 三条路线对比

| 路线 | 成本 | 优势 | 劣势 |
|------|------|------|------|
| A 原生 App（Swift/Kotlin 或 RN/Flutter 重写） | 3-6 月 | 完整移动体验 | 4363 行 GUI + 核心逻辑全重写；EXIF 写入 iOS 有权限墙；维护双端 |
| B 桌面端 Web 面板（FastAPI + 手机浏览器访问） | 2-4 周 | 复用全部 Python 核心；手机平板即开即用；与 tailnet 看板习惯一致 | 需电脑开着服务（用户主机长期开机✅）；写入仍回桌面批处理 |
| C iOS Shortcuts/快捷指令 + EXIF 小工具 | 1-2 周 | 零代码量 | 只能覆盖"查看"不能"写入"；体验割裂 |

## 结论与推荐

**推荐 B（Web 面板）作为"移动端支持"的第一步**：
1. 复用 core/ 全部能力（解析/匹配/预览），只加一个薄 Web 层
2. 主机常开 + Tailscale 域名已有（m2-max.tail801360.ts.net）——手机在任何网络直接访问
3. 天然兼容 iPad 大屏（旅行中回看轨迹+照片映射最舒服的设备）
4. 可与即将做的 Map view（任务 #7）共享轨迹渲染逻辑

原生 App（A）留作远期：等 Web 面板验证"移动查看"需求真实存在且用户强烈需要"手机直接写入"时再评估。
