## Bug 列表

### BUG-1：跳过照片污染自动跟随邻居 + 计算GPS列误显

**两个现象同根因，合并处理。**

#### 现象 A：自动跟随将"已跳过"照片作为有效邻居

- **测试版本**：8b4a7ce
- **Case**：
  ```
  文件名                                            日期时间        GPS(前)            GPS(后)           方式          状态
  DSC02444.JPG                                     2026/2/17 15:46  无                 24.9586,102.7565  就近          成功
  DSC02446_edit_501546108302115.jpg                2026/2/17 16:49  24.9586,102.7565   24.9586,102.7565  已跳过        已跳过
  DSC02447.JPG                                     2026/2/17 16:51  无                 24.9586,102.7565  自动跟随上一个 成功
  ```
- **问题**：02447 (16:51) 自动跟随了上一个"已跳过"的 02446 (16:49)
  - 时间差仅 2 分钟，在 isolated_window 内 → 阈值检查通过
  - 但 02446 的 GPS 是照片自带原始 GPS（与 02444 相同，来自 15:46）
  - 02447 拿到的实际是 1 小时前的位置

#### 现象 B：跳过照片的"计算GPS"列不应显示值

- **问题**：已跳过照片（method=skipped）的"计算GPS"列显示了原有 GPS 值
- **期望**：跳过的照片没有进行计算，"计算GPS"应显示"—"

#### 根因链（同一根因）

1. `gps_matcher.py` 第 43 行，跳过时设置 `gps=photo.existing_gps`（应为 `None`）
2. worker 从 `result.gps` 取值填入计算GPS列 → 触发现象 B
3. `_second_pass_neighbor_follow` 第 56 行，`succeeded` 列表筛选条件为 `r.success and r.gps`，未排除 `r.method=="skipped"` → 跳过照片被纳入有效邻居 → 触发现象 A

```
gps_matcher.py skip 逻辑（第 39-46 行）:
  if photo.has_gps and not overwrite_gps:
      results.append(MatchResult(
          photo=photo, success=True, method="skipped",
          gps=photo.existing_gps,  ← BUG: 不应设置
      ))

gps_matcher.py 第二回合（第 56 行）:
  succeeded = [(i, r) for i, r in enumerate(results)
               if r.success and r.gps and r.photo.timestamp]
  ← BUG: 缺少 r.method != "skipped" 条件
```

#### 修复方案

**两处修改，共同解决两个现象：**

| # | 文件 | 位置 | 修改 |
|---|------|------|------|
| 1 | `gps_matcher.py` | 第 43 行 | 跳过时 `gps=None` |
| 2 | `gps_matcher.py` | 第 56 行 | succeeded 列表增加 `r.method != "skipped"` |

- 修改 1 直接修复现象 B（计算GPS列不再有值）
- 修改 1 + 修改 2 双重保障修复现象 A（跳过照片不再被选为邻居）
- GPS(后) 列不受影响：GUI 层对 skipped 行从 GPS(前) 取值，逻辑独立

#### 测试要求

- 新增测试 case：skipped 照片介于两张无 GPS 照片之间，验证自动跟随不选 skipped 邻居
- 验证 skipped 照片的 result.gps 为 None
- 回归验证：正常邻居跟随仍工作

- **相关文件**：`gps_matcher.py`, `worker.py`, `main_window.py`

### BUG-2：GPS覆盖率统计回归（v0.17.0 BUG-1 修复引入）

- **测试版本**：a10a074+
- **现象**：GPS覆盖率显示 `43.2% → 50.7%`，期望 `43.2% → 93.8%`
- **Case**：146 张照片，63 张已有 GPS，83 张无 GPS → 算法匹配成功 74 张 → 最终仅 9 张无 GPS
  - 期望覆盖率：137/146 = 93.8%
  - 实际显示：74/146 = 50.7%（漏算了 63 张 skipped 照片）
- **根因**：v0.17.0 BUG-1 修复将 skipped 照片 `result.gps` 改为 `None`，导致 worker 层 `latitude=None`。覆盖率计算（`main_window.py:784-788`）用 `latitude is not None` 判断"有GPS"，skipped 照片被排除
- **修复**：`main_window.py` 第 784-788 行，`gps_with_result` 应同时计入 skipped 照片
  ```python
  # 当前（buggy）:
  gps_with_result = sum(
      1 for d in details
      if d.get("success") and d.get("method") != "protected"
      and d.get("latitude") is not None
  )

  # 修复：
  gps_with_result = sum(
      1 for d in details
      if d.get("method") != "protected"
      and (d.get("latitude") is not None or d.get("method") == "skipped")
  )
  ```
- **同时检查**：`_update_pre_process_summary`（第 1278 行）的覆盖率口径是否一致
- **相关文件**：`main_window.py`

## 功能列表

### FEAT-1：默认排序改为按日期时间

- **需求**：结果列表默认按日期时间升序排列，而非文件名
- **场景**：在其他设备上编辑照片后，文件名可能完全改变（如 `DSC02446_edit_501546108302115.jpg`），但 EXIF 日期时间保持不变。按文件名排序时这些照片会散落各处，按时间排序才能还原实际拍摄顺序
- **实现**：
  - 匹配完成后，列表按日期时间列升序排列作为默认排序
  - 用户仍可点击列头手动切换排序方式
- **相关文件**：`result_table.py`, `main_window.py`

### FEAT-2：经纬度展示切换（单行/双行）

- **需求**：GPS 坐标列支持单行和双行两种展示方式，方便纵向对比
- **当前**：`24.9586, 102.7565`（一行，逗号分隔）
- **期望**：可切换为单元格内换行：
  ```
  24.9586
  102.7565
  ```
- **交互**：
  - 列表上方、筛选下拉右侧，增加经纬度展示切换按钮（单行/双行）
  - 默认单行模式
  - 切换双行时：行高自动适配、行号列正常显示、单元格内容垂直居中
- **适用列**：GPS(前)、计算GPS、GPS(后) 三列
- **相关文件**：`result_table.py`, `main_window.py`

### FEAT-3：跟随方式标签统一 + 备注区分来源

- **需求**：方式列不区分"手动跟随"和"自动跟随"，统一标签；手动/自动的区别放到备注列
- **当前**：方式列有 `跟随上一个` 和 `自动跟随上一个` 两个标签，用户困惑
- **调整后**：
  - 方式列：`就近` / `插值` / `跟随上一个` / `跟随下一个`（不区分手动/自动）
  - 备注列：`算法第二回合` / `Review选择` / `列表手动选择`（体现操作来源）
- **影响范围**：
  - method label 映射（`auto_follow_prev` → `跟随上一个`）
  - 备注生成逻辑（worker / main_window）
- **相关文件**：`result_table.py`, `main_window.py`, `worker.py`
