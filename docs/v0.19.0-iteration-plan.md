# v0.19.0 迭代计划

记录于 2026-05-17。
测试版本：a10a074（v0.17.0）

## Bug 列表

### BUG-1：覆盖写入后列表计数翻倍

- **测试版本**：a10a074
- **现象**：覆盖模式下写入完毕后，列表计数从 129 变成 258（恰好翻倍）
- **根因**：
  1. 预览匹配阶段：Worker 通过 `photo_signal` 逐张 emit → `_on_photo_processed` 向列表 insertRow，共 129 行
  2. 写入阶段（COPY/OVERWRITE）：Worker 的 `write_phase` 也有 `on_photo` 回调，同样 emit `photo_signal`（worker.py 第 279 行）
  3. `_on_photo_processed` 再次被调用，在已有 129 行基础上再追加 129 行 → 258 行
  4. `_on_step3_execute`（第 640-652 行）创建新 Worker 传 `pre_computed_results`，但没有清空已有列表行
- **修复方向**：
  - 方案 A：`_on_step3_execute` 执行写入前不清空列表，但 `_on_photo_processed` 在写入阶段不新增行，而是更新已有行（按文件名匹配）
  - 方案 B：写入阶段的 `photo_signal` 不用于更新列表，只用 `done_signal` 更新统计。写入进度通过 `progress_signal` 展示
  - 方案 C：写入阶段 emit 不同的信号（如 `write_signal`），GUI 层只更新已有行的写入状态列（新增"写入状态"列：已复制/已覆盖/跳过）
  - **推荐方案 C**：语义清晰，且满足用户提出的"加一列写入状态"需求
- **相关文件**：`worker.py`, `main_window.py`, `result_table.py`

### BUG-2：覆盖写入完成弹窗延迟出现

- **测试版本**：a10a074
- **现象**：覆盖写入完成后，完成弹窗有时很晚才出现，甚至下一轮任务已经开始时上一轮的弹窗才弹出
- **根因**：
  1. `_on_done`（第 1146 行）使用 `QMessageBox.information` 模态弹窗
  2. 如果写入线程已完成但 GUI 事件队列中有待处理的用户交互事件，弹窗被排队
  3. 用户在等待期间可能已经点击了新操作（如再次预览），弹窗出现在错误的上下文中
- **修复方向**：
  - 方案 A：用非阻塞通知替代 `QMessageBox`（如 statusBar 提示 + 短暂 toast）
  - 方案 B：弹窗前检查当前状态，如果已开始新一轮操作则跳过弹窗
  - 方案 C：写入完成后弹窗前加状态检查 `_is_processing`，若已在新任务中则仅更新 statusBar
  - **推荐方案 C**：保留弹窗但加状态保护，不影响正常流程
- **相关文件**：`main_window.py`

## 功能列表

### FEAT-1：新增"写入状态"列

- **需求**：结果列表增加一列显示每张照片的写入状态（复制/覆盖/跳过/未写入）
- **场景**：
  - 预览匹配完成后，写入状态为空
  - COPY 执行后，已写入的行标记"已复制"
  - OVERWRITE 执行后，已写入的行标记"已覆盖"
  - 跳过的行标记"跳过"
  - 失败的行标记"未写入"
- **列位置**：状态列之后，备注列之前（第 7 列）
- **同时修复 BUG-1**：写入阶段 emit 专用信号 `write_signal`，GUI 层只更新写入状态列，不新增行
- **相关文件**：`result_table.py`, `main_window.py`, `worker.py`
