# GPS Photo Tracker - 需求分析文档

**版本：** v2.0
**日期：** 2026-05-05
**基于：** gps-photo-tracker v7.2.0 代码审查 + 用户访谈

---

## 1. 项目定位

### 1.1 核心目标

**一句话：批量处理本地/网络磁盘上的照片，根据 GPX 轨迹给照片打 GPS 标签（写入 EXIF）。**

### 1.2 为什么要做这件事

- 旅行拍了大量照片，手机 GPS 可能关闭或信号差，照片没有位置信息
- 手上有 GPS 记录仪/运动手表导出的 GPX 轨迹文件
- 需要把 GPS 坐标和照片按时间对齐，写入照片 EXIF，使照片管理软件（Photos、Lightroom 等）能按地点整理照片

### 1.3 用户场景

1. **典型用户**：个人开发者/摄影爱好者
2. **使用频率**：旅行后批量处理，非日常工具
3. **数据规模**：一次处理 100-5000 张照片，10-100 个 GPX 文件
4. **数据来源**：本地磁盘、外接硬盘、网络磁盘（SMB/NFS 挂载）
5. **输出目标**：照片获得正确的 GPS EXIF 信息，可被照片管理软件识别

## 2. 完整功能清单

### 2.1 核心功能（必须有，否则不可发布）

#### CF-01：GPX 文件解析

- 解析 GPX 1.0/1.1 格式
- 支持多文件（一次加载整个目录）
- 支持 multi-track、multi-segment
- 提取轨迹点：时间戳（UTC）、纬度、经度、海拔
- 时区处理：UTC → 本地时间，内部统一用 UTC 时间戳
- 按 segment 分组，不跨段匹配

#### CF-02：照片扫描与读取

- 递归扫描指定目录（rglob）
- 支持格式：JPEG (.jpg/.jpeg)、PNG (.png)
- 读取 EXIF 拍摄时间（DateTimeOriginal > DateTimeDigitized > DateTime）
- 识别已有 GPS 信息的照片
- 统计扫描结果（总数、有 GPS 数、无 GPS 数）

#### CF-03：GPS 时间匹配算法

- **分层策略**：
  - 中间照片（前后照片都在 context_window 内）：使用线性插值匹配
  - 孤立照片（前后照片超出 context_window）：使用就近匹配
- **距离校验**：前后 GPS 点距离 > 阈值时拒绝匹配（防 GPS 跳变）
- **分段隔离**：照片时间必须在某个 GPS segment 的时间范围内
- **match_tail 控制**：可选择是否匹配尾部/头部孤立照片
- **所有参数必须生效**：构造参数必须在算法逻辑中被消费

#### CF-04：GPS 坐标写入 EXIF

- 写入 GPS IFD 到 EXIF
- GPS 版本：2.3.0.0（EXIF 2.3 标准）
- 包含：纬度（DMS + Ref）、经度（DMS + Ref）、海拔（精度 0.01m）
- 保留原始 EXIF 其他字段（拍摄时间、相机信息等）
- 海拔 = 0 时正确写入（不能被当成 False 丢弃）
- 负海拔正确处理（GPSAltitudeRef = 1）

#### CF-05：输出模式

- **预览模式**（Dry Run）：只显示匹配结果，不修改任何文件
- **拷贝模式**（推荐）：复制照片到输出目录 + 写入 GPS
  - 所有照片都必须输出（成功/失败/跳过一律拷贝）
  - 可选保持原有目录结构
  - 输出数量 == 输入数量
- **覆盖模式**（需确认）：直接修改原文件

#### CF-06：GPS 数据保护

- 默认跳过已有 GPS 的照片（保护数据）
- 可选覆盖已有 GPS（用户显式确认）
- 覆盖时记录新旧 GPS 对比日志

### 2.2 基本功能（第一版应有的体验）

#### BF-01：参数配置

| 参数 | 默认值 | 范围 | 说明 |
|------|--------|------|------|
| 孤立照片时间窗口 | 300 秒 (5分钟) | 60-3600 | 孤立照片的最大时间差 |
| 中间照片时间窗口 | 3600 秒 (1小时) | 600-7200 | 中间照片的最大时间差 |
| 上下文窗口 | 300 秒 (5分钟) | 60-1800 | 判断照片是否"夹在中间" |
| GPS 距离阈值 | 200 米 | 50-1000 | 前后 GPS 最大距离 |
| match_tail | True | True/False | 是否匹配首尾孤立照片 |
| 时间偏移 | 0 秒 | -3600~3600 | 照片时间修正值 |

- 所有参数有合理默认值（经过真实数据调优）
- 参数变更实时生效

#### BF-02：进度反馈

- 显示当前处理阶段（扫描 GPS → 扫描照片 → 匹配 → 写入）
- 显示进度百分比和数量（当前/总数）
- 支持取消操作
- 预估剩余时间

#### BF-03：结果报告

- 统计：总数、匹配成功、跳过（已有 GPS）、失败、成功率
- 失败原因分类：
  - GPS 数据缺失（不在任何 segment 覆盖范围内）
  - GPS 时间差过大
  - GPS 距离过大（跳变）
  - 尾部孤立照片（match_tail=False 时）
- 日志记录到文件（可离线查看）

#### BF-04：容错处理

- 单张照片处理失败不影响整体
- 单个 GPX 文件解析失败跳过
- 文件权限错误/磁盘错误记录日志继续
- 所有异常都记录到日志（不能只打印到控制台）

#### BF-05：日志系统

- 操作日志：任务开始/结束、参数、统计
- 匹配日志：每张照片的匹配结果
- 写入日志：GPS 写入操作、覆盖记录
- 错误日志：异常、警告

### 2.3 增强功能（后续迭代）

#### EF-01：真正的 GPS 线性插值

- 对中间照片，根据前后 GPS 点按时间比例计算经纬度
- 预期提升成功率从 83% 到 90%+
- 需要验证精度是否满足要求

#### EF-02：HEIC/HEIF 支持

- iPhone 默认 HEIC 格式，piexif 不直接支持
- 方案：用 pillow-heif 做格式转换，或使用其他 EXIF 库
- 需要评估转换后的画质损失

#### EF-03：并发处理

- 多线程/多进程并发写入
- 目标：500 张/分钟（当前 305 张/分钟）
- 注意线程安全和资源管理

#### EF-04：断点续传

- 大批量处理中断后可恢复
- 记录已处理的照片列表
- 重启后跳过已完成的

#### EF-05：智能参数推荐

- 分析 GPX 密度（点/分钟）和照片分布（张/小时）
- 自动推荐最优时间窗口参数
- 减少用户调参成本

#### EF-06：照片预览与地图标记

- 显示照片缩略图
- 在地图上显示匹配的 GPS 位置
- 可视化 GPS 轨迹和照片位置关系

#### EF-07：交互式确认

- 匹配后逐个审核确认
- 拒绝不满意的匹配
- 手动调整 GPS 位置

#### EF-08：多 GPS 格式支持

- KML（Google Earth）
- TCX（Garmin）
- 自定义 JSON

#### EF-09：导出报告

- HTML 报告（含图表）
- JSON 结构化数据
- 按日期/地点汇总

#### EF-10：图片方向自动调整

- 读取 EXIF Orientation 标签
- 自动旋转到正确方向
- 显示时应用旋转（不修改原始文件）

## 3. 现有实现评估

### 3.1 合适的部分（应保留/沿用）

| 模块 | 评价 | 理由 |
|------|------|------|
| **GPS 匹配算法 V3** | 核心价值 | 83.1% 成功率，经过 1832 张照片实测验证 |
| **分层匹配策略** | 设计合理 | middle/isolated 分层、距离校验、分段隔离 |
| **EXIF 处理** | 功能完整 | 读写正确，GPS 版本 2.3 标准，海拔精度 0.01m |
| **GPX 解析** | 功能完整 | 支持多 track/segment，时区转换正确 |
| **拷贝模式** | 安全机制 | 不动原文件，所有照片都输出，防丢失 |
| **GPS 覆盖保护** | 安全机制 | 默认跳过已有 GPS 的照片 |
| **日志系统** | 可追溯 | 4 类日志，操作可审计 |

### 3.2 不合适的部分（需重构/替换）

| 模块 | 问题 | 严重度 |
|------|------|--------|
| **tkinter 桌面应用** | UX 差，缩略图加载慢，大列表卡顿，平台外观不一致 | 高 |
| **FastAPI Web 服务** | 偏离目标——用户要的是本地批处理工具，不是 Web 服务 | 高 |
| **desktop_app.py 1200 行** | UI + 业务逻辑 + 文件 IO 混杂，不可维护 | 高 |
| **单线程处理** | 1832 张照片需要 6 分钟，无并发 | 中 |
| **HEIC 支持声称** | piexif 不支持 HEIC，但代码声称支持 | 中 |
| **硬编码时区偏移** | UTC+8 写死，不通用 | 低 |
| **无断点续传** | 大批量处理中断后从头开始 | 低 |
| **无真正的 GPS 插值** | 名叫"插值匹配"但实际只找最近点，没有线性插值 | 低 |

### 3.3 关键设计缺陷

**问题 1：桌面应用 vs Web 应用的方向混乱**

原始需求（DESKTOP_APP_REQUIREMENTS.md）明确说"Web 应用无法获取完整文件路径"所以要做桌面应用。但代码里同时维护了桌面应用和 Web 服务两套入口，Web 服务还额外加了本地路径支持（`gpx_dir`/`photo_dir` 参数），等于把桌面应用的能力硬塞进 Web 框架。

**建议**：既然目标是本地批量处理，应该回归桌面应用方向。Web 服务可以作为可选的远程访问能力，但不应该是主入口。

**问题 2：没有真正的 GPS 插值**

V3 算法叫"插值匹配"，但 `find_best_match` 方法里实际只做了"找最近的 GPS 点"（`closest_point`），没有根据前后 GPS 点做线性插值计算中间位置。这可能是成功率没有进一步提升的原因。

## 4. 非功能需求

### NFR-01：平台支持

- 主要平台：macOS
- 理论支持：Windows、Linux

### NFR-02：性能

- 处理速度 ≥ 500 张/分钟（并发优化后）
- 内存占用 ≤ 500MB（5000 张照片时）

### NFR-03：安全性

- 不上传照片到任何服务器
- 拷贝模式保证所有照片都有输出
- 操作可撤销（通过备份或拷贝模式）
- 测试时不得修改原始测试数据

### NFR-04：易用性

- 最少步骤完成操作：选 GPX → 选照片 → 开始
- 参数有合理默认值
- 结果清晰易懂

### NFR-05：代码质量

- UI / Service / Algorithm / IO 四层分离
- 跨模块数据结构用 dataclass/TypedDict 定义，禁止字符串键名隐式约定
- 所有资源操作用 context manager
- 所有 except 块必须有日志

## 6. 建议的技术方向

### 6.1 架构

```
┌─────────────────────────────────┐
│           CLI / GUI             │  ← 用户入口
├─────────────────────────────────┤
│         Service Layer           │  ← 业务编排
│  (match, batch, report)         │
├──────────┬──────────┬───────────┤
│ GPXParser│EXIFWriter│GPSMatcher │  ← 核心算法
├──────────┴──────────┴───────────┤
│         File Access Layer       │  ← 文件系统抽象
│  (local, network, read, write)  │
└─────────────────────────────────┘
```

### 6.2 关键改进点

1. **分层解耦**：UI → Service → Algorithm → IO，每层独立可测
2. **真正的 GPS 插值**：提升成功率从 83% 到可能 90%+
3. **并发处理**：multiprocessing 或 asyncio，目标 500 张/分钟
4. **文件系统抽象**：统一处理本地和网络磁盘
5. **参数自动调优**：根据 GPX 密度和照片分布推荐参数
